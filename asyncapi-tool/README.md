## Overview

The AsyncAPI contract is a specification that creates an event-driven architecture based contract for APIs by detailing all of its resources and channels in a human and machine-readable format for easy development, discovery, and integration. The Ballerina AsyncAPI tool generates Ballerina code from an AsyncAPI definition, and AsyncAPI definitions from Ballerina code.

What the tool generates depends on the protocol and on what you give it as input:

| Protocol | Input | Output |
|----------|-------|--------|
| `http` | An AsyncAPI definition | A webhook listener: event types, service types, the listener and the dispatcher |
| `ws` | An AsyncAPI definition | A WebSocket client |
| `ws` | A Ballerina package or a standalone `.bal` file | An AsyncAPI definition of its WebSocket services |

The tool requires Ballerina Swan Lake Update 13 (2201.13.0) or later.

## Usage

```bash
bal asyncapi [OPTIONS] <input>
```

`<input>` decides the direction:

- An AsyncAPI definition (`.yaml`, `.yml` or `.json`) generates Ballerina code. The protocol comes from the definition: a definition with `x-ballerina-event-identifier` is a webhook trigger (`http`), and one with a `ws` or `wss` server is a WebSocket client (`ws`). A definition that shows neither needs `--protocol`; the tool does not guess.
- A Ballerina package directory or a standalone `.bal` file generates an AsyncAPI definition. A `.bal` file that belongs to a package is not accepted; pass the package directory instead, as `bal run` does. A package in a workspace is read on its own; a workspace root is not accepted.

### Options

| Option | Description |
|--------|-------------|
| `-n`, `--dry-run` | List the files the run would write, without writing anything. |
| `--force` | Overwrite existing files without asking. |
| `-h`, `--help` | Print the help. |
| `--license <file>` | Put this license at the top of generated `.bal` files. The file must contain only `//` comment lines and blank lines. |
| `--module <name>` | Read services from, or generate code into, this module of the package. A module that doesn't exist yet is created. Not used with a standalone `.bal` file. |
| `-o`, `--output <dir>` | Write the files to this directory. Defaults to the current directory. Generated Ballerina code must go into a package. |
| `--output-format <text\|json>` | Print the result, warnings and errors as text or as JSON lines. Defaults to text in a terminal and JSON when the output is piped or redirected. |
| `--protocol <http\|ws>` | The protocol to generate for. Defaults to the one the definition shows. |
| `--service <path>` | Generate the definition of this service only: its base path, for example `/chat`, or the name of the service class it upgrades to, for example `ChatService`. |
| `--spec-format <yaml\|json>` | Write the generated definition as YAML or JSON. Defaults to `yaml`. `--format` still works, with a warning. |
| `--spec-side <client\|service>` | Read the definition as written from this side. Defaults to `client`; use `service` for a definition written from the server's side. `ws` only. |
| `-V`, `--version` | Print the tool's version. |
| `--with-tests` | Generate tests along with the code. For `http`, the definition needs `x-ballerina-auth`. |

An option that does not apply to what you are generating is ignored with a warning, for example `--spec-format` when generating code. Run `bal asyncapi --help` for the same list.

### Existing files

Every check runs before anything is written: the arguments, the input, the license, the output location and whether each file can be written. If any check fails, nothing is written. Then, for every file the tool generates:

- a file that does not exist yet is created;
- a file that already has the same content is left alone;
- a file with different content is only replaced when you agree to it.

In a terminal the tool lists the files it would replace and asks once. Without a terminal, for example in a script or a CI workflow, it does not ask: it stops with exit code 4 and writes nothing. Pass `--force` to replace the files without asking.

```
$ bal asyncapi slack-events.yaml
bal asyncapi: error: types.bal already exists
  Re-run with --force to overwrite.
  Try: bal asyncapi slack-events.yaml --force
```

To see what a run would do before running it, add `--dry-run` (or `-n`). It runs the same checks, never asks, and lists the files:

```
$ bal asyncapi slack-events.yaml --dry-run
would overwrite  types.bal
Dry run: nothing was written.
```

Each generated `.bal` file starts with the `--license` text, if given, and a line that says it was generated by `bal asyncapi`.

### Output and exit codes

The result (the files written) goes to stdout, and warnings and errors go to stderr. With `--output-format json`, or when the output is not a terminal, each report is one JSON object per line, for example:

```json
{"files":[{"path":"client.bal","action":"created"},{"path":"types.bal","action":"unchanged"}]}
{"severity":"error","kind":"overwrite-refused","message":"types.bal already exists","suggestion":"Re-run with --force to overwrite.","command":"bal asyncapi slack-events.yaml --force"}
```

A warning about the definition names its place in the file, for example `chat.yaml:12:5: warning: ...`.

The tool exits with the codes every Ballerina CLI tool uses:

| Code | Meaning |
|------|---------|
| 0 | The run succeeded, or a dry run passed every check |
| 1 | Invalid input, a definition the tool can't generate from, or a file that can't be written |
| 2 | Invalid command line, such as a missing input or an unknown option value |
| 3 | The input or output is not a valid package or standalone file |
| 4 | Files would be replaced, and you declined or the tool could not ask |

Generating an AsyncAPI definition compiles the package with the dependency versions in its `Dependencies.toml`. A package without one fails with exit code 1; run `bal build` once to create it.

## Examples

### Generate a webhook listener from an AsyncAPI definition

```bash
# Into the package in the current directory
bal asyncapi slack-events.yaml

# Into another package, replacing files generated earlier
bal asyncapi slack-events.yaml -o ./slack-listener --force

# Into a module of the package
bal asyncapi slack-events.yaml --module events
```

### Generate a WebSocket client from an AsyncAPI definition

```bash
bal asyncapi chat-api.yaml

# With tests and a license header
bal asyncapi chat-api.yaml -o ./chat-client --with-tests --license ./license.txt

# A definition whose servers don't say ws or wss
bal asyncapi chat-api.yaml --protocol ws
```

### Generate an AsyncAPI definition from Ballerina code

```bash
# Every WebSocket service in the package in the current directory
bal asyncapi .

# One service, as JSON
bal asyncapi . --service /chat --spec-format json -o ./specs

# Services in one module of the package
bal asyncapi . --module chat

# A standalone file
bal asyncapi chat_service.bal
```

## Webhook listeners

### Sample AsyncAPI definition

```yaml
asyncapi: 3.0.0
info:
  title: Slack Events
  version: 1.0.0
x-ballerina-event-identifier:
  type: body
  path: event.type
channels:
  app:
    address: app
    messages:
      appMention:
        x-ballerina-event-type: app_mention
        summary: Subscribe to only the message events that mention your app or bot
        payload:
          $ref: "#/components/schemas/GenericEventWrapper"
      appRateLimited:
        x-ballerina-event-type: app_rate_limited
        summary: Indicates that your app's event subscriptions are being rate limited
        payload:
          $ref: "#/components/schemas/GenericEventWrapper"
operations:
  app:
    action: receive
    channel:
      $ref: "#/channels/app"
    messages:
      - $ref: "#/channels/app/messages/appMention"
      - $ref: "#/channels/app/messages/appRateLimited"
components:
  schemas:
    GenericEventWrapper:
      title: Standard event wrapper for the Events API
      type: object
      required:
        - event
      properties:
        event:
          title: The actual event, an object, which happened
          type: object
          required:
            - type
            - event_ts
          properties:
            type:
              title: The specific name of the event
              type: string
            event_ts:
              title: When the event was dispatched
              type: string
            text:
              title: The message content
              type: string
```

Every event the listener should handle is a message of a channel, and every channel is listed in a `receive` operation.

The extensions starting with `x-ballerina` tell the tool how to dispatch events. They must be added to the definition before using the tool.

1\. `x-ballerina-event-identifier` - When the listener receives an event, there should be a way to identify the event type. This has two parts, `type` and `path`.

- `type` - Either `header` or `body`: whether the event type arrives as an HTTP header or as an attribute in the body.
- `path` - The header name if the type is `header`, or the JSON path of the attribute if the type is `body`.

2\. `x-ballerina-event-type` - This should be there in every message inside the channel. It is the value the identifier above has for that event.

3\. `x-ballerina-event-label` (optional) - By default, the generated remote function's name and doc comment are derived directly from `x-ballerina-event-type`. This works well when that value is itself a clean, readable string (e.g. `company.propertyChange`), but some real event sources use type strings with a required prefix/suffix that only makes sense for matching (e.g. a CloudEvents-style `qbo.account.merged.v1`), which produces an awkward function name if used for naming too (`onQboAccountMergedV1`). Set `x-ballerina-event-label` on a message to control the generated name independently (e.g. `AccountMerged` produces `onAccountMerged`), without changing the value actually compared against incoming payloads.

4\. `x-ballerina-auth` (optional) - How the listener verifies that a request really comes from the event source, for example an HMAC signature header. See the [webhook signature DSL reference](https://github.com/ballerina-platform/asyncapi-tools/blob/main/docs/webhook-dsl-reference.md).

### Generated files

Generating a listener writes these files:

1. `types.bal` - the Ballerina data types extracted from the AsyncAPI definition
2. `service_types.bal` - the service types for the events described in the definition
3. `listener.bal` - the HTTP listener that receives the events
4. `dispatcher_service.bal` - the logic that dispatches each event to its remote function

At the root of a package, it also writes the trigger's compiler plugin to `lib/` and a `CompilerPlugin.toml` for it, so apps built with `--export-endpoints` list the trigger's services (see [Exporting trigger endpoints](#exporting-trigger-endpoints)).

With `--with-tests`, the tool also writes `tests/dispatch_test.bal`, which sends signed sample events to the listener and checks that each reaches its remote function. The events are signed, so this needs `x-ballerina-auth` in the definition; without it the tool warns and writes no tests.

The tests read one sample event per event type from `tests/resources/trigger_payloads/<event>.json`, for example `tests/resources/trigger_payloads/order_created.json`. The tool doesn't write these, as real sample events can't be made up from the definition, so add them before running `bal test`:

```json
{"type": "order_created", "orderId": "A-1001", "customerId": "C-7", "total": 59.90}
```

If your package has `configurable` values without defaults, such as the shared secret, also give them in `tests/Config.toml`.

When modifying the generated code, keep the following in mind.

- All the incoming requests are received by the resource method in the `dispatcher_service.bal` file. Hence, if there is a necessity to add an authentication logic for the incoming calls, that logic can be included there before processing the incoming HTTP request.
- If more information is needed when initializing the listener such as secrets, endpoint URLs, tokens, refresh tokens, etc., update the `init` function in the `listener.bal` file.

### Using the generated listener

1\. Create a package with `bal new slack_listener` and generate the listener into it:

```bash
cd slack_listener
bal asyncapi slack-events.yaml
```

2\. Add a service for the events to `main.bal`:

```ballerina
listener Listener webhookListener = new ({}, 8090);

service AppService on webhookListener {
    remote function onAppMention(GenericEventWrapper event) returns error? {
        // Implement the logic to use the received `event` here.
    }

    remote function onAppRateLimited(GenericEventWrapper event) returns error? {
        // Implement the logic to use the received `event` here.
    }
}
```

3\. Execute `bal run`.

### Choosing the path

A service without a path receives events at `/`. Give it a path to receive them somewhere else. This also lets several triggers, or your own HTTP services, share one port:

```ballerina
listener http:Listener httpListener = new (8090);
listener github:Listener githubListener = new ({webhookSecret: githubSecret}, httpListener);
listener slack:Listener slackListener = new ({verificationToken: slackToken}, httpListener);

service github:PushService /github on githubListener { ... }   // http://host:8090/github
service slack:AppService /slack on slackListener { ... }       // http://host:8090/slack
```

Services on the same path share its dispatcher, so each service type can be attached once per path. Detaching the last service on a path frees that path.

## Exporting trigger endpoints

`bal build --export-endpoints` lists the ports and paths a program listens on in `target/artifact/endpoints.yaml`. The `ballerina/http` compiler plugin only reports services attached to an `http:Listener`, so each trigger package ships its own compiler plugin to report services attached to its `Listener`, with the same rules and defaults as HTTP services (`type: "REST"`, an empty `schemaPath`).

Ballerina runs a compiler plugin only for apps that import its package directly, so the plugin has to be inside the trigger package. The plugin jar ships inside this tool. Generating a listener at the root of a package writes it to `lib/asyncapi-trigger-compiler-plugin.jar`, with a `CompilerPlugin.toml` that points to it:

```toml
# CompilerPlugin.toml
[plugin]
id = "asyncapi-compiler-plugin"
class = "io.ballerina.asyncapi.trigger.plugin.AsyncAPICompilerPlugin"

[[dependency]]
path = "lib/asyncapi-trigger-compiler-plugin.jar"
```

Commit both files with the trigger's source. `bal pack` puts the jar in the trigger's bala, and apps that use the trigger get the plugin from there, so nothing else needs to be installed or run.

Both files follow the same rules as the generated code: an existing file that differs is only replaced when you agree or pass `--force`, and `--dry-run` lists them. Generating with a newer tool updates the jar to that tool's plugin. A trigger generated with 0.13.3 has a `[[tool.asyncapi]]` entry in `Ballerina.toml` that copied the jar during the build; generating again removes it and keeps the rest of the file, which the result lists as `merged`. A package can have only one compiler plugin, so if it already has another, the tool leaves it as it is and warns. A listener generated into a module (`--module`) gets no plugin, as the plugin belongs to the package.

The endpoints are exported with Ballerina 2201.13.6 and later. On earlier versions the plugin logs a warning and the build carries on. The plugin source is in [`asyncapi-trigger-plugin`](../asyncapi-trigger-plugin).
